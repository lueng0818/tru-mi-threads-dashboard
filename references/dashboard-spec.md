# Tru-Mi Threads Dashboard — 產品規格與 UI 驗收

> 建立於 2026-09-11。
> 語氣規則在 `jessica-voice.md`，證據在 `jessica-voice-samples.md`，
> 每日流程在 `daily-sop.md`，IA 遷移計畫在 `ia-migration-plan.md`。
> **本檔不重複定義其他檔已有的規則，只引用。**

## 0. 產品目標

Jessica 打開後，能很快知道三件事：

```
今天可以發什麼？
現在有誰值得回？要怎麼回？
最近大家在聊什麼，可以延伸什麼？
```

其他分析、證據、規則全部往後藏。

**主畫面做決策，第二層看原因，第三層才讀完整規則。**

### 0.1 這不是文案生成器

```
❌ 怎樣讓 Jessica 的留言更完整？
✅ Jessica 現在最自然的下一句是什麼？
```

如果答案只有 6 個字，就只給 6 個字。
但「最自然的下一句」是**聽懂之後**才知道的事，不是先射箭再畫靶。

## 1. 資訊架構

```
頂部常駐   🔍 搜尋題目、貼文、留言
底部主導覽  今天 ｜ 回留言 ｜ 有後續 ｜ 找題目
```

| 入口 | 責任 |
|---|---|
| **今天** | 告訴 Jessica 現在最值得做什麼 |
| **回留言** | 真正處理留言的工作區 |
| **有後續** | 只收 Jessica 已參與、且**對方之後又有新回覆**的對話 |
| **找題目** | 主動找靈感 |

搜尋是工具不是目的地，固定在頂部，不佔底部主導覽。

### 1.1 今天

```
今天已互動
8 則

目前找到
20 則值得互動

優先看看
① …  ② …  ③ …  ④ …  ⑤ …

［查看全部 20 則］
```

還包含：今天可以發什麼、有後續幾則、今天可以去聊的話題。

### 1.2 回留言

分三種：別人回我的貼文｜我留言後對方又回我｜我可以加入聊聊的陌生貼文

每則核心畫面：

```
【他在說什麼】     一句話，整理對方真正的重點
【建議怎麼接】     接住／追問／共聊／回答／專業補充／先確認
【Jessica 可以怎麼回】  一個最自然的下一句

［為什麼這樣建議？ ▸］   ← 想看才展開
```

⛔ 預設**不展開**：為什麼符合品牌、Voice 分析、Evidence 分析、CTA 分析、完整 SOP。

### 1.3 有後續

**收件條件（三項全中）**

```
① Jessica 已在該對話中回覆過
② Jessica 最後一次回覆「之後」，對方又出現 NEW reply
③ Jessica 尚未回覆該則 NEW reply
```

⛔ 沒有新回覆的不進來。**等待不是待辦。**

保留完整 thread context：對方留言 → Jessica 回覆 → 對方新回覆 → Jessica 下一句

### 1.4 找題目

```
婚戒 ｜ 戒圍／佩戴 ｜ 客製設計 ｜ 感情／婚姻 ｜ 籌備婚禮 ｜ 最近 Threads 在聊什麼
```

既有四大焦慮軸（溝通與翻車／日常佩戴／預算審美／傳承情感）**保留為內部判讀軸**，
退到第二層，不重新分類既有卡片。詳見 `ia-migration-plan.md` 決策 B。

### 1.5 議題小樹

```
戒指拔不出來
├─ 📌 原始貼文（原文／發文者在說什麼／為什麼值得看）
├─ 🔥 N 則值得看的留言          ← N 是真實數字
├─ 💬 正在進行的對話（待回／已回有後續）
├─ 🧠 大家在意什麼
└─ 🌱 可以延伸（繼續聊／設計師觀點／下一篇 Threads／延伸閱讀）
```

**延伸閱讀必須與當下節點相關**，不是把整份 SOP 端出來。

## 3. 數量規則（UI 驗收）

```
總數     = 當下真實數量
首頁預覽  = 少數高優先項目
工作區    = 全部，可一路處理到底
```

**三者不得混為一談。**

### 3.1 不設每日上限

系統負責找和排序，**不負責決定 Jessica 今天該回幾則**。
今天找到 20 則，她可以回 3 則、10 則或全部 20 則。

⛔ 不得顯示 `8/20`、百分比、完成率、進度條。
「今天已互動 8 則」是已完成的互動，**不暗示還欠 12 則**。

### 3.2 所有數字必須來自真實資料

`3`、`5` 這類數字只能來自當下真實資料或 UI 預覽數量，
**不得成為 Jessica 每日回覆／海巡的固定上限。**

### 3.3 關鍵留言 ≠ Top 5

「今天找到多少值得互動的貼文」與「某篇貼文裡有多少值得看的留言」是**兩個不同概念**，
不得共用 Top-N 邏輯。

```
某篇有 47 則留言，判斷其中 7 則值得看  → 顯示「7 則值得看的留言」
只有 2 則有價值                      → 顯示「2 則值得看的留言」
```

⛔ 禁止：固定 Top 5｜補滿 5 則｜「五大留言」｜「前五大留言」

**不必硬湊。** 資料只有 2–3 種真正不同的聲音時，顯示 2–3 則比硬塞五則更符合 Evidence Gate。

### 3.4 選件依據不是讚數

目標不是「最熱門留言」，是「**最有助 Jessica 理解這個議題與人**的留言」。

綜合判斷：互動量｜是否代表常見需求／觀點｜是否提供不同角度｜
是否出現真實經驗｜是否存在值得回應的問題｜是否能延伸下一輪對話

⛔ 不得選出多則意思完全相同的留言。高讚但重複時保留代表性最高的一則，位置留給不同觀點。

## 4. 「今天值得回」與「回留言」刻意重複

**這是 UI 驗收規則，不是建議。**

```
「今天值得回」= 通知／入口
「回留言」    = 完整工作區
```

⛔ **不得因為 UI 去重、DRY、避免重複等理由刪掉其中之一。**

（就像信箱的紅點與信箱本身。合併會讓首頁失去「今天」的功能。）

## 5. Selection Evidence（首頁排序與關鍵留言共用）

排序可以自動，**理由必須可追溯**。

正常畫面只提供一個入口：`為什麼先看這幾則？ ▸`

展開後給人類可理解的理由（例：「對方正在問戒圍問題」「Jessica 有真實經驗可以接」
「目前討論還在進行」）。**更底層才保存完整 Evidence，不把工程資料攤在 UI 上。**

L4 Evidence 保存：

```
Top-N Selection Evidence

入選：
#12｜高互動＋分享不同方法｜代表「處理方式」
#18｜真實疼痛經驗｜代表「實際困擾」
#27｜詢問戒圍｜代表「明確求助」

未入選：
#03｜高讚，但與 #12 觀點高度重複
#09｜只有表情符號，缺乏可分析內容
#21｜互動高，但與目前議題關聯低
```

保存欄位：candidate → selected / not selected → 理由 → 代表的需求／觀點 → 使用的 signals

## 6. 工作區三種處理結果

```
回覆 ｜ 晚點再看 ｜ 看過了，不回
```

「看過了，不回」**不是失敗**，是 Jessica 已經做完判斷。選後移出當日主要清單，但保留原因。

### 6.1 原因分兩類，處置不同

**一般不回 → discovery feedback**

```
不對頻 ｜ 已有人回答得很好 ｜ 沒有適合我加入的地方 ｜ 其他
```

**有風險 → 走既有 L3，不是降權**

```
有風險
→ 依 daily-sop.md Step 6.9 走 L3 OBSERVE_ONLY
→ 不產生留言建議、不進一般互動待辦
→ 保存觀察紀錄與判定理由
```

⛔ **本檔不重新定義什麼叫風險、哪些內容屬 L3。**
Canonical owner 是 `daily-sop.md` Step 6.9，日後規則變更只改那一處。

⚠️「Jessica 不回」與「系統判定不應介入」是兩件不同的事。

### 6.2 這些原因不是拿來評分 Jessica

它們是改善系統的訊號，不是她的績效。

## 7. Discovery Feedback 迴路

```
單筆 feedback
  ↓ 只記錄，不調整
累積多筆
  ↓ 確認是否集中於相同特徵
提出調整假設
  ↓ 保存調整前設定
  ↓ 記錄：為什麼調／調了什麼／使用哪些訊號
執行調整
  ↓ 觀察結果

改善      → 保留調整，留下驗證結果
無差異／變差 → 回復調整前設定
           → 記錄「假設不成立」
           → 該訊號回到累積階段，不得自動重複套用同一假設
```

⛔ **單一「不回」不得變成 discovery 規則**（適用 `jessica-voice.md` §0 Rule Generalization Gate）。

沒有回退路徑，discovery 只會單向越調越窄，而且沒人知道是什麼時候開始的。

## 8. 卡片 Schema

### 8.1 post-card 屬性

| 屬性 | 值 | 說明 |
|---|---|---|
| `data-level` | A／B／C／D／RISK | 既有，不變 |
| `data-keywords` | 空白分隔 | 既有，見 §8.4 |
| `data-collected` | YYYY-MM-DD | 既有，收錄日 |
| `data-topic` | 婚戒／戒圍佩戴／客製設計／感情婚姻／籌備婚禮／新發現／**待分類** | 新增，題材軸 |
| `data-convo` | active／inactive／none | 新增 |
| `data-convo-last` | YYYY-MM-DD | 新增，最後一次有新回覆的日期 |
| `data-enriched` | YYYY-MM-DD／unavailable | 新增，分析日（與 `data-collected` 分開） |

⛔ 證據不足時 `data-topic` 一律填 `待分類`，**不得硬分類**。

### 8.2 comments-section 新增區塊

```html
<div class="key-comments" data-count="3" data-short-reason="僅 3 則具代表性">
  <div class="key-comment"
       data-intent-primary="分享方法"
       data-intent-signals="自身經驗 想知道後續"
       data-intent-uncertainty="…">…</div>
</div>
<div class="listener-analysis">…他在說什麼／建議怎麼接／可以怎麼回…</div>
<div class="convo-thread">…</div>
<div class="selection-evidence">…</div>
```

### 8.3 data-intent 三層（不採封閉單選）

```
data-intent-primary      主要互動目的（必填）
data-intent-signals      0–N 個補充訊號
data-intent-uncertainty  需要時標記不確定
```

合法 primary：`分享方法`｜`實際困擾`｜`求助`｜`不同觀點`｜`閒聊`｜`認同`｜`想知道後續`

實際留言常常同時是好幾種（「我也是欸！之前卡到最後去急診，妳朋友後來有拿下來嗎？」
＝自身經驗＋共鳴＋想知道後續）。**不得為了 schema 完整而虛構 signals。**

### 8.4 `data-keywords` 的真實行為（2026-09-11 更正）

`cardMatchesKw()` 的判斷是：

```js
return terms.some(t => dk.indexOf(t) >= 0 || txt.indexOf(t) >= 0);
```

**是 OR，不是 fallback。** 全文比對（貼文原文＋留言）一直都在跑。

所以舊敘述「省略會讓 JS 退回全文比對，搜尋品質變差」**是錯的**——省略不會降低既有 recall。
它的作用是**加分**：讓卡片能被「原文沒有 literal 出現、但主題相關」的詞找到。

```
❌ 無效：把原文已有的詞抄進 data-keywords 衝覆蓋率（對搜尋結果零影響）
✅ 有效：只補「原文沒有、但使用者會拿來查」的同義詞與上位詞
```

（2026-09-11 現況：229 張卡中 102 張無 `data-keywords`，覆蓋率 55%。
實際需要補的遠少於 102 張——只補主題相符但字面不含的組合。）

### 8.5 P1–P3 不使用 side-car JSON

`tools/deploy_verify.sh` 的 `FILES` 寫死兩份 HTML，且該腳本**不得修改**。
資料放 `data/*.json` 會造成「HTML 驗證 DEPLOY_VERIFIED，但資料檔沒推上去」的**靜默失敗**。

→ **P1–P3 新資料一律內嵌 HTML。**

## 10. UI 驗收清單

```
□ 數量全部來自真實資料
□ 無固定 3／5 則限制
□ 無「五大留言／前五大留言」字樣
□ 無互動完成率／進度條／百分比
□ 【他在說什麼】不是原文換句話說
□ 回覆深度依互動情境，未套全域字數（依類型看分布）
□ AI 未自行加入 Jessica 第一人稱情緒鏡頭（搜尋應為 0）
□ 未把觀察／推論升格成市場事實（無來源之市場結論詞應為 0）
□ 首頁排序理由可追溯
□ 「今天值得回」與「回留言」皆存在，未被去重
□ 「有風險」接到 SOP Step 6.9 L3，未在本檔重新定義
□ Discovery feedback 有累積、調整、驗證與 rollback
□ 舊 41 個首頁入口未保留為主要體驗
```

### 10.1 Positive Validation（不可跳過）

上面全是**防錯檢查**，全過只代表沒有發現已知失敗，**不代表對 Jessica 有用**。

Jessica 用真實工作情境走一次：

```
打開 → 看今天 → 挑值得互動的 → 看「他在說什麼」→ 看建議
→ 決定回／晚點／不回 → 處理有後續 → 找新題目
```

核心不是問「畫面喜不喜歡」，而是：

```
① 有沒有讓她更快判斷值得跟誰聊？
② 建議有沒有真的幫她接下一句，而不是增加閱讀工作？
③ 她是否仍保有自己決定回不回、怎麼回的控制權？
```

⛔ **不得因 automated checks 全 PASS 就跳過這一關。**
第③項尤其關鍵：一個把所有事都決定好的儀表板，會比 41 個按鈕的版本更難用。

## 11. 資料遷移

採 **forward-only + on-demand enrichment**，不批次重做 229 張舊卡。詳見 `ia-migration-plan.md`。

歷史證據三態：

```
current                 即時重抓成功
historical:YYYY-MM-DD   重抓失敗，改用既有快照分析（UI 須明顯標示）
unavailable             連快照都不足
```

⛔ **不得把 historical snapshot 顯示成 current**，也不得因重抓失敗就丟棄既有證據。
